# Audyt kodu — YouTube Subscription Monitor

**Data:** 2026-04-04  
**Zakres:** cały kod projektu (~1500 linii, 5 plików Python)

## Ocena ogólna: 6.5/10

---

## Problemy krytyczne

### 1. Bezpieczeństwo: credentials w repozytorium
- `youtube_client.py:19` — `CLIENT_SECRET_FILE` z pełną nazwą pliku w kodzie
- `.gitignore` nie wyklucza `credentials.pickle` ani `client_secret_*.json`
- `credentials.pickle` zawiera token OAuth i nie powinien być w repo

### 2. Brak thread-safety w SQLite
- `database.py:13` — `check_same_thread=False` pozwala na dostęp z wielu wątków, ale brak locka
- `background_sync` w `main.py` pisze do bazy z wątku tła, a TUI czyta z głównego
- Rozwiązanie: dodać `threading.Lock` do klasy `Database`

### 3. Połykanie wyjątków bez logowania
- `youtube_client.py:176-177` — `except HttpError: pass` — ciche ignorowanie błędów API
- `tui.py:157-158` — `except: pass` (bare except) w `_open_in_browser`
- `tui.py:179` — `except: pass` w `_set_shorts_threshold`

---

## Problemy strukturalne

### 4. `tui.py` — 850 linii, God Class
- Klasa `YouTubeTUI` to 820+ linii z całą logiką: renderowanie, input handling, nawigacja, Kitty protocol, clipboard, konfiguracja
- Metoda `run()` (linie 448-844) to ~400 linii monolityczna pętla z zagnieżdżonymi if/elif

### 5. Powtarzający się wzorzec (~10 razy)
```python
curr = -1
for idx, item in enumerate(self.display_items):
    if item["type"] == "video" and item["original_index"] == self.selected_index:
        curr = idx; break
```
Wystarczyłaby jedna metoda `_find_current_display_index()`.

### 6. Kruchy system indeksów
- `selected_index` odnosi się do pozycji w `self.videos`, a `display_items` mają `original_index` mapujący z powrotem
- Zmiana sortowania `self.videos` po sync przesuwa wszystkie indeksy — podatne na błędy

### 7. Brak walidacji danych z API
- `youtube_client.py:159` — porównanie dat jako stringów (`video_pub_at < published_after`) działa dla ISO 8601, ale jest kruche
- `models.py:45-53` — `duration_seconds` zwraca 0 dla nierozpoznanych formatów (cicha degradacja)

---

## Problemy mniejsze

### 8. Hardkodowane wartości
- `youtube_client.py:226` — `max_workers=20` — za dużo dla YouTube API, ryzyko rate-limitingu
- `main.py:39` — `max_workers=10` dla thumbnails
- `tui.py:207` — fallback `16, 8` px na komórkę
- `youtube_client.py:108` — `.rjust(7)` — magic number

### 9. Martwy kod i nieużywane importy
- `youtube_client.py:197` — `raw_map` budowane w pętli, ale nigdzie nie używane poniżej
- `database.py:2` — `import json` — nieużywane
- `youtube_client.py:6` — `Any` z typing — nieużywane
- `models.py:3` — `import json` + metoda `to_dict()` — prawdopodobnie nieużywane w kodzie

### 10. Powtórzony timestamp
- `main.py:61` i `main.py:76` — `now_rfc3339` generowane dwa razy (mogą się różnić o sekundy)

### 11. Brak testów
- Zero testów w projekcie

## Co jest dobrze zrobione

- **Adaptive batching** (`youtube_client.py:122-142`) — sprytna optymalizacja quota API
- **Thread-safe YouTube service** (`_get_service_for_thread`) — poprawne użycie `threading.local()`
- **Kitty protocol** z cache'owaniem i poprawnym enkodowaniem chunków
- **Merge z zachowaniem `watch_later`** przy sync (`tui.py:491-496`)
- **Vim-like navigation** z countami (5j, 3J, nG, gg, zz) — dobrze przemyślane
- **Czytelne modele danych** — dataclasses w `models.py`
- **ON CONFLICT** w SQLite zamiast sprawdzania istnienia — poprawne

---

## Rekomendacje (priorytetyzowane)

1. Dodać `.gitignore` wpisy dla `credentials.pickle`, `client_secret_*.json`, `sync_error.log`
2. Dodać `threading.Lock` do klasy `Database` i opakowywać operacje zapisu
3. Wyodrębnić `_find_current_display_index()` — eliminacja ~10 powtórzeń
4. Logować błędy API zamiast `pass` — chociaż do `sync_error.log`
5. Usunąć martwy kod — `raw_map` w `get_detailed_videos`, nieużywane importy
